# File Upload

Attach evidence to the right pull request and leave a verifiable, readable record.

GitHub's documented arbitrary-file upload path is the web UI. Use `gh` for PR discovery and verification, and use the browser composer for the actual attachment. Do not invent an API upload endpoint or claim success before the attachment is visible in the PR.

## Invocation gate

Reach for this skill only when all of these conditions hold:

- The user explicitly requests file upload, attachment, publication, or visual evidence, or explicitly names `$file-upload`.
- The change affects a user-visible UI surface, such as layout, styling, responsive behavior, a modal, or motion.
- The requested evidence files exist and are safe to publish.

When the work is backend-only, or when the user only asks to create or update a PR, complete the PR workflow without invoking this skill. For mixed work, require an explicit request for UI evidence before proceeding.

## Workflow

### 1. Resolve the PR

Inspect the current branch before opening anything:

```bash
gh pr view --json number,url,state,isDraft,title,headRefName
```

If no PR belongs to the current branch, find the matching head branch explicitly:

```bash
gh pr list --state open --head "$(git branch --show-current)" --json number,url,title,headRefName
```

Use the existing open PR. Stop and ask for a target when more than one candidate remains. Do not create a PR as part of this skill.

### 2. Check every file

Resolve the exact paths supplied by the user and inspect them before upload:

```bash
file path/to/evidence
du -h path/to/evidence
```

For screenshots, inspect the image before publishing it. For videos, confirm that it is the intended short recording and has no sensitive overlays. Keep before/after files paired and name their role in the comment.

Exclude secrets, credentials, access tokens, `.env` files, private keys, raw production data, and logs containing personal or agency-sensitive information. Treat a public-repository upload as public; private and internal repository uploads remain restricted to repository viewers. If a file is unsafe or ambiguous, stop before opening the composer.

### 3. Choose the PR surface

Prefer a timeline comment when the PR already exists or when adding new evidence. Use the PR description only when the user explicitly wants the body updated and the existing body can be preserved.

Open the GitHub composer:

```bash
gh pr comment <PR> --web
```

In the web composer, attach each local file with the attachment control or drag-and-drop, then use a compact evidence comment such as:

```markdown
## Visual evidence

- Before: [what this image shows]
- After: [what this image shows]
- Video: [what interaction or timing this recording demonstrates]
```

Keep the Markdown generated by GitHub for the attachments. Add descriptive alt text or nearby labels, and preserve the order `Before`, `After`, then `Video` when those categories apply.

If browser automation cannot operate a file chooser, hand off only that mechanical step: give the user the exact PR URL and exact filenames to attach. Continue only after the user confirms submission or the browser shows the published comment. Never substitute a guessed URL or an unverified local path.

### 4. Verify publication

After submitting, verify the same PR:

```bash
gh pr view <PR> --comments
```

For a description update, also inspect the body:

```bash
gh pr view <PR> --json body,url
```

Confirm that every requested file has a rendered attachment or GitHub-generated link, the labels explain what each artifact proves, and no sensitive content was published. Report the PR URL, placement, filenames, and any file that was skipped. Say `not uploaded` when verification is incomplete.

## Boundaries

- Use `gh pr comment --body-file` only for text that already contains usable URLs; it does not upload local binary files.
- Skip this skill for backend-only issues and for UI issues where the user did not request file publication.
- Keep large or unsupported artifacts out of the PR unless the user chooses an approved repository-specific artifact or release workflow.
- Do not commit screenshots or recordings merely to manufacture an upload URL.
- Do not replace required motion evidence with a still image.

Official references: [Attaching files on GitHub](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files) and [`gh pr comment`](https://cli.github.com/manual/gh_pr_comment).
